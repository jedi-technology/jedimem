Never run `git add` or `git commit` from a background process in a repo a human
is also using.

**Why:** `.git/index.lock` is a mutex, not a queue — it fails immediately rather
than waiting. Measured: 20 concurrent porcelain commits landed only 2 commits and
committed 7 of 20 files. The other 13 stayed on disk as untracked and were
silently lost, while git printed *"Another git process seems to be
running… remove the file manually"* — which makes the user's git look broken.

**How to apply:** build the tree with plumbing against a private index
(`GIT_INDEX_FILE`, created with `mktemp -u` — git rejects an existing empty index
file), then compare-and-swap a ref outside `refs/heads/`. Read the parent commit
*before* building the tree, or the CAS succeeds while committing a stale tree and
silently drops other writers' work.
