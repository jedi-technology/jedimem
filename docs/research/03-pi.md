# pi 0.84.2, reverse-engineered

**Identity (VERIFIED):** `@earendil-works/pi-coding-agent` v0.84.2, npm global,
entry `dist/cli.js`, 11 MB `dist/`. Upstream monorepo:
`github.com/earendil-works/pi-mono`. Config dir `.pi` (declared as
`piConfig.configDir` in `package.json`).

**Method:** pi ships its own unminified documentation and TypeScript examples in
the published package (`docs/*.md`, `examples/`). That is authoritative primary
source, not guesswork — everything below is VERIFIED from it or from `--help`
unless labelled otherwise.

## Executive summary — the load-bearing facts

1. **pi has the best integration surface of the three agents by a wide margin:**
   a first-class in-process TypeScript extension API with **32 lifecycle
   events**, not a spawn-a-subprocess hook system.
2. **`pi.on("context", ...)` fires before every LLM call and can rewrite the
   entire message array.** This is total context control — strictly more powerful
   than Claude Code's or Codex's capped string injection.
3. **pi natively reads `AGENTS.md` *and* `CLAUDE.md`.** Confirmed by the
   `--no-context-files` flag: *"Disable AGENTS.md and CLAUDE.md discovery and
   loading."* So **jedimem needs no pi integration at all for delivery** — the
   compiled files already work.
4. **pi supports the exact team-distribution model jedimem wants, natively.**
   Project settings at `.pi/settings.json` are committable, and *"pi installs any
   missing packages automatically on startup after the project is trusted."*
   Commit one file; every teammate is provisioned on next launch. **No install
   command.**
5. **Sessions are JSONL with a `parentId` tree**, branching *in place* rather
   than by forking a new file — different from Claude Code, and it means one
   file can contain several divergent histories.
6. **Sessions are auto-migrated (rewritten) on load** across format versions.
   A bare byte-offset checkpoint is therefore unsafe here too.
7. **v3 renamed the `hookMessage` role to `custom`** — extension-injected
   messages are identifiable, which is the self-amplification guard for pi.
8. Headless mode: `--print/-p` with `--mode json`, plus an RPC mode and an SDK.

## Extension API

```typescript
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  pi.on("session_start", async (_event, ctx) => { /* ... */ });
  pi.on("tool_call", async (event, ctx) => {
    if (event.toolName === "bash" && event.input.command?.includes("rm -rf")) {
      /* block or modify */
    }
  });
}
```

The docs state the capability set plainly: *"They can subscribe to lifecycle
events, register custom tools callable by the LLM, add commands, and more"* and
*"Event interception — Block or modify tool calls, inject context, customize
compaction."*

### All 32 events (VERIFIED, extracted from `docs/extensions.md`)

| Group | Events |
|---|---|
| Startup | `project_trust`, `resources_discover` |
| Session | `session_start`, `session_info_changed`, `session_before_switch`, `session_before_fork`, `session_before_compact`, `session_compact`, `session_before_tree`, `session_tree`, `session_shutdown` |
| Agent | `before_agent_start`, `agent_start`, `agent_end`, `agent_settled`, `turn_start`, `turn_end` |
| Message | `message_start`, `message_update`, `message_end` |
| Tool | `tool_call`, `tool_result`, `tool_execution_start`, `tool_execution_update`, `tool_execution_end` |
| Model/provider | `context`, `before_provider_headers`, `before_provider_request`, `after_provider_response`, `model_select`, `thinking_level_select` |
| Input | `input`, `user_bash` |

Three of these have no analogue in the other agents and matter a lot:

**`context`** — the delivery mechanism:
```typescript
pi.on("context", async (event, ctx) => {
  // event.messages - deep copy, safe to modify
  return { messages: filtered };
});
```
*"Fired before each LLM call. Modify messages non-destructively."* Full read and
rewrite of the message array on every call. Where Claude Code gives us a
10,000-char string slot, pi gives us the whole context.

**`session_before_compact` / `session_compact`** — Claude Code's hard limitation
is that **nothing can inject after compaction**. pi exposes compaction as an
interceptable event, so memories can be re-asserted across a compaction boundary.

**`before_provider_request`** — access to the outbound request itself. Powerful,
and a place to be disciplined: jedimem should not touch it. Rewriting provider
requests is how a memory tool becomes the prime suspect for every unrelated bug.

**`agent_settled`** — a natural, cheap trigger for batched extraction: the agent
has stopped working, so capture now rather than mid-turn.

### Extension locations (VERIFIED)

| Location | Scope |
|---|---|
| `~/.pi/agent/extensions/*.ts` | global |
| `~/.pi/agent/extensions/*/index.ts` | global |
| **`.pi/extensions/*.ts`** | **project-local** |
| **`.pi/extensions/*/index.ts`** | **project-local** |

*"Project-local `.pi/extensions` entries load only after the project is
trusted."* Same trust-gate concept as Codex's hash pinning, and the docs are
blunt about the stakes: *"Extensions run with your full system permissions and
can execute arbitrary code. Only install from sources you trust."*

Note `.pi/extensions/` is **in-repo and committable** — jedimem's pi integration
can ship in the repo exactly like the Codex hooks file.

## Distribution — the part that changes jedimem's install story

```bash
pi install npm:@foo/bar@1.0.0
pi install git:github.com/user/repo@v1
pi install ./relative/path/to/package
pi install -l <source>      # write to PROJECT settings, not user settings
pi update --all             # update packages, reconcile pinned git refs
pi -e <source>              # try without installing (temp dir, this run only)
```

The decisive sentence from `packages.md`:

> By default, `install` and `remove` write to user settings
> (`~/.pi/agent/settings.json`). Use `-l` to write to project settings
> (`.pi/settings.json`) instead. **Project settings can be shared with your team,
> and pi installs any missing packages automatically on startup after the project
> is trusted.**

So for pi, the entire jedimem install is one committed file:

```json
{ "packages": ["git:github.com/jedi-technology/jedimem@v1"] }
```

A teammate clones the repo, launches pi, trusts the project, and jedimem is
installed. This is the closest thing to the stated goal — *"just read the repo,
install it, and you're good to go"* — that exists in any of the three tools, and
it should be the model we push the others toward.

Version pinning is supported (`npm:pkg@1.2.3`, `git:...@v1`) and
`pi update --all` "reconciles pinned git refs", so the supply-chain posture is
pin-by-default rather than track-HEAD. jedimem must ship a pinned ref in the
committed settings, never a floating branch.

## Session format (VERIFIED from `docs/session-format.md`)

```
~/.pi/agent/sessions/--<path>--/<timestamp>_<uuid>.jsonl
```
where `<path>` is the cwd with `/` replaced by `-`. **Lossy and irreversible**,
the same trap as Claude Code's `projects/<slug>` encoding: read `cwd` from inside
the file, never reconstruct it from the directory name.

JSONL, one object per line with a `type` field. Entries form a **tree via
`id`/`parentId`**, *"enabling in-place branching without creating new files."*
Consequences for a reader:

- One file may contain multiple divergent branches. Ingesting it linearly will
  mix abandoned branches with the real history. **We must walk `parentId` from
  the active leaf**, not read top to bottom.
- Because branching is in place, the *file* is stable across forks — but the
  *meaning* of earlier lines can change.

Versions: v1 linear (legacy), v2 tree, v3 renamed `hookMessage` → `custom`.
*"Existing sessions are automatically migrated to the current version (v3) when
loaded."*

**Two hard consequences:**

1. **Files are rewritten, not just appended.** A migration on load rewrites the
   file wholesale. A byte-offset checkpoint would silently resume into garbage.
   Fingerprint the head and track size — the same guard the Claude Code reader
   needs, for a different reason.
2. **`role: "custom"` is the self-amplification guard.** Extension-injected
   content lands with role `custom`. jedimem must *exclude* `custom` messages
   from extraction, or it will re-ingest the memories it just injected and
   inflate their confidence with no new evidence — the failure that produced
   mem0's 808 duplicate "prefers Vim" entries. This is the pi analogue of
   dropping Claude Code's `hook_success` attachment.

Content blocks are typed: `text`, `image` (base64), `thinking`, `toolCall`.
Note `thinking` here carries a real `thinking: string` field — unlike Claude
Code, where all observed thinking blocks were empty. UNVERIFIED whether it is
populated in practice, but if it is, pi is the one agent where assistant
reasoning is actually minable.

## Headless / extraction runtime

`--print/-p` with `--mode text|json|rpc`, plus `--no-tools`, `--tools`,
`--exclude-tools`, `--system-prompt`, `--append-system-prompt`, `--thinking`,
`--no-session` (ephemeral), and `--provider`/`--model`/`--api-key`.

Two things make pi the *best* extraction runtime of the three, if a user has it:

- **`--no-tools` / `-nt` genuinely disables tools.** On Claude Code,
  `--disallowedTools` removes the permission but still bills the tool
  definitions (~27.5k tokens fixed — see `07-monitor-runtime.md`). If `-nt`
  drops the definitions from the request, pi's fixed overhead should be a small
  fraction of that. **UNVERIFIED — measure before relying on it**; it is the
  single highest-value open measurement in this document.
- **`--no-session`** means extraction runs leave no session file, so the monitor
  cannot accidentally ingest its own extraction sessions as new material. On the
  other agents we must filter those out explicitly.

`--provider` defaults to `google` and `--api-key` "defaults to env vars", so pi
is BYO-key rather than bundled-auth. That weakens the zero-config story for pi
specifically: we can borrow Claude Code's login, but pi needs a key the user
already configured. Detect and fall back rather than prompt.

## What this means for jedimem

| Need | Mechanism | Confidence |
|---|---|---|
| **Delivery (bulk)** | **nothing to build** — pi reads `AGENTS.md`/`CLAUDE.md` natively | high |
| **Delivery (precise)** | `pi.on("context")` — full message-array control | high |
| **Delivery across compaction** | `session_before_compact` / `session_compact` | high |
| **Capture** | `pi.on("turn_end")` / `agent_settled` in-process | high |
| **Capture (fallback)** | tail `~/.pi/agent/sessions/--<path>--/*.jsonl`, walking `parentId` | high |
| **Install** | committed `.pi/settings.json` + pinned package ref | high |
| **Extraction runtime** | `pi -p --mode json --no-tools --no-session` | medium (overhead unmeasured) |
| **Self-amplification guard** | exclude `role: "custom"` | high |
| **Do not touch** | `before_provider_request` | — |

### The strategic read

pi is the reference target: it can do everything we need, and its committed
`.pi/settings.json` gives us auto-provisioning that neither other tool matches.
But it is also the *least* common of the three in practice, so the honest
sequencing is to design against Claude Code's and Codex's shared hook schema
(the lowest common denominator) and treat pi's extension API as the *premium*
path that unlocks compaction-survival and precise context control where available.

Concretely: **the same memory files must produce a good result with zero pi
integration** (via compiled `AGENTS.md`) and a *better* result with the extension
installed. Never make the extension load-bearing.

## Open questions

- Fixed token overhead of `pi -p --no-tools` versus `claude -p`'s measured
  ~27.5k. If pi's is genuinely small, pi becomes the preferred extraction
  runtime whenever it is installed.
- Whether `thinking` content is actually populated (it is always empty on Claude
  Code).
- Whether `pi.on("context")` return values are size-capped.
- Exact `.pi/settings.json` schema beyond `packages` and `extensions`, and how
  project and user settings merge (override vs concatenate — this determines
  whether a committed setting can clobber a teammate's personal config, which
  would be unacceptable).
- Whether the project-trust prompt can be satisfied non-interactively in CI.
